# Миграции Room

Локальная база — источник истины для каталога тикеров и офлайн-избранного.
Избранное переживает переустановку только через Firestore, всё остальное при
потере базы придётся выкачивать заново. Поэтому разрушающей миграции здесь нет.

## Как это устроено

- Схема объявлена в `local/CryptoCompareDatabase.kt`, `exportSchema = true`.
- Экспортированные схемы лежат в `core/data/schemas/` и **коммитятся**.
  Каталог задан в `build.gradle.kts` через `room { schemaDirectory(...) }`.
- Миграции — это sql-файлы в `src/main/assets/migrations/migration_<from>_<to>.sql`.
  `AssetMigrations.loadAll(context)` собирает их по именам файлов, поэтому
  `DatabaseModule` трогать не нужно: новая миграция подключается добавлением файла.
- В `DatabaseModule` **нет** `fallbackToDestructiveMigration`. Если миграции не
  хватает, Room падает с `IllegalStateException` — это осознанно: лучше заметный
  сбой на отладке, чем молча стёртая база у пользователя.

> `fallbackToDestructiveMigration(false)` **не** отключает разрушающую миграцию.
> Аргумент называется `dropAllTables` и лишь выбирает, сносить ли таблицы, которыми
> Room не управляет. Сам вызов её включает. Не возвращайте его «чтобы не падало».

## Как добавить миграцию

1. Поменяйте `@Entity`.
2. Поднимите `version` в `@Database` на единицу.
3. Создайте `src/main/assets/migrations/migration_<N>_<N+1>.sql` с ручным SQL.
4. Соберите модуль — появится `core/data/schemas/<...>/<N+1>.json`. **Закоммитьте его.**
5. Добавьте тест миграции в `CryptoCompareDatabaseMigrationTest` (в файле лежит
   готовый шаблон) и прогоните на устройстве:
   ```bash
   ./gradlew :core:data:connectedDebugAndroidTest
   ```

Шаг 4 обязателен: без свежего json `runMigrationsAndValidate` не с чем сверять
результат, и расхождение схемы с Entity вылезет уже у пользователя.

## Ограничения sql-файлов

Сплиттер режет файл по `;`, комментарии `--` вырезаются построчно. Значит:

- **триггеры и строковые литералы с `;` внутри писать нельзя** — такую миграцию
  оформляйте кодом через `AssetMigrations.createMigration` или отдельным `Migration`;
- одна инструкция — один `;`, пустые строки допустимы.

SQLite не умеет `ALTER TABLE ... DROP COLUMN` и смену типа: чтобы изменить колонку,
создайте новую таблицу, перелейте данные `INSERT INTO ... SELECT`, удалите старую и
переименуйте новую. Если данные при этом не нужны (как в `migration_3_4.sql`, где
каталог всё равно перекачивается с бэкенда), допустимо просто пересоздать таблицу —
но **никогда** так с `favourite_tickers`.

## История версий

| Версия | Что изменилось |
|---|---|
| 1–3 | до появления экспортированных схем; миграций в репозитории нет |
| 4 | `symbols` пересоздана с `updatedAt` и `syncedAtMillis` (`migration_3_4.sql`) |
| 5 | добавлена `catalog_remote_key` для `RemoteMediator` (`migration_4_5.sql`) |

Схема экспортируется начиная с версии 5 — она и есть точка отсчёта. Пути с
устройств, где база осталась версии 1–3, не покрыты: там миграции нет, и Room
упадёт. Это касается только сборок до появления `migration_3_4.sql`.
